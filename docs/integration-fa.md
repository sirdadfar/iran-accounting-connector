# راهنمای یکپارچه‌سازی — iran-accounting-connector

این سند مسیر عملی «از نصب بسته تا اولین سند واقعی» را توضیح می‌دهد. برای دستور زبان نگاشت فیلدها
[`mapping-fa.md`](mapping-fa.md)، برای کدهای خطا [`errors-fa.md`](errors-fa.md) و برای اجرای ورکر
[`deployment-fa.md`](deployment-fa.md) را ببینید.

> **پیشفرض صادقانه:** این بسته هیچ اتصال تأییدشده‌ای به محک، هلو یا سپیدار ندارد. یک قرارداد
> JSON/HTTP قابل‌تنظیم و تست‌شده دارد. نام فیلدها و URLها را از مستندات **همان نسخه‌ی نصب‌شده** پر کنید و
> روی یک شرکت/سال مالی آزمایشی تأیید کنید.

---

## ۱. پیش از نوشتن کد

۱. **مستندات نسخه‌ی نصب‌شده** را بگیرید: راهنمای API، فایل WSDL، نمونه‌ی درخواست‌ها یا مستندات
   افزونه. اگر مستندات وجود ندارد، این کار ابتدا باید به یک «فاز کشف» تبدیل شود، نه حدس زدن.
۲. **یک شرکت آزمایشی** در نرم‌افزار حسابداری بسازید. هرگز اولین سند را در دفاتر واقعی ثبت نکنید.
۳. **دسترسی شبکه** را روشن کنید: از سرور ورکر به `host:port` مقصد. اگر TLS با گواهی داخلی است،
   مسیر CA را به `CurlClient` بدهید؛ `verify_peer` را خاموش نکنید.
۴. **جای رمز** را مشخص کنید: توکن در متغیر محیطی یا فایل خارج از مخزن، نه در `config` کامیت‌شده.
۵. **صف** را انتخاب کنید. این کتابخانه را داخل درخواست HTTP فروشگاه اجرا نکنید؛ سفارش را در صف
   بگذارید و با ورکر پردازش کنید.

## ۲. انتخاب نوع رابط

| رابط مقصد | وضعیت در این بسته | کار شما |
| --- | --- | --- |
| REST/JSON | `GenericWebserviceAdapter` پیاده‌سازی و تست‌شده | پر کردن `endpoints` و `mapping` |
| SOAP/XML | پیاده‌سازی نشده | یک کلاس با `ConnectorInterface` بنویسید و همان Runner/Retry/Store را استفاده کنید |
| دیتابیس مستقیم SQL Server | فقط اسکلت آزمایشی (`SqlServerAdapter`) | بررسی اسکیما با DBA و پیاده‌سازی اختصاصی؛ نوشتن حدسی ممنوع |
| فایل/CSV | پیاده‌سازی نشده | اتصال‌دهنده‌ی اختصاصی |

برای SOAP لازم نیست منطق سینک را بازنویسی کنید؛ فقط `ConnectorInterface` را پیاده کنید:

```php
final class CustomerSoapAdapter implements \IranAccounting\ConnectorInterface
{
    public function pushInvoice(\IranAccounting\Domain\Invoice $invoice): \IranAccounting\Http\PushReceipt
    {
        $response = $this->client->call('InvoiceCreate', $this->mapInvoice($invoice));

        return new \IranAccounting\Http\PushReceipt((string) $response->Id, ['raw' => (array) $response]);
    }

    // pushPayment, upsertCustomer, findInvoice, healthCheck, capabilities, name
}
```

اگر `capabilities()[Capabilities::IDEMPOTENCY_HEADER]` را `false` بگذارید، `OperationRunner` تلاش
مجدد خودکار را غیرفعال می‌کند و هشدار `IR-IDEM-003` می‌دهد. این رفتار عمدی است: یک POST بدون کلید
جلوگیری از تکرار می‌تواند سند را دوبار ثبت کند.

## ۳. پیکربندی گام‌به‌گام

### ۳.۱. فایل پیکربندی

```php
<?php
// /etc/shop-sync/erp.php — خارج از مخزن، فقط خواندنی برای کاربر ورکر
return [
    'name'      => 'customer-x-erp',                  // بخشی از namespace کلید idempotency
    'base_uri'  => getenv('ERP_BASE_URI'),             // مثال: https://erp.customer.local/api/v1
    'headers'   => [
        'Authorization' => 'Bearer ' . getenv('ERP_TOKEN'),
        'X-Tenant'      => getenv('ERP_TENANT') ?: 'default',
    ],
    'timeout'   => 15.0,
    'endpoints' => require __DIR__ . '/erp-endpoints.php',
    'mapping'   => require __DIR__ . '/erp-mapping.php',
];
```

قواعدی که سازنده بررسی می‌کند:

* `base_uri` مطلق با `http`/`https`، بدون `user:pass`، بدون query و fragment.
* مسیر مطلق اندپوینت باید همان origin باشد؛ برای مقصد دیگر اتصال‌دهنده‌ی جدا بسازید.
* هدرها باید نام معتبر RFC 7230 و مقدار بدون CR/LF/NUL داشته باشند.
* `idempotency_header` خالی یعنی «کلید نمی‌فرستم»؛ در این حالت تلاش مجدد خودکار محدود می‌شود.
* `timeout` باید عددی متناهی و بزرگ‌تر از صفر باشد.

### ۳.۲. اندپوینت‌ها

```php
<?php
return [
    'invoice'      => ['method' => 'POST', 'path' => '/invoices',          'id_path' => 'data.id'],
    'payment'      => ['method' => 'POST', 'path' => '/payments',          'id_path' => 'data.id'],
    'customer'     => ['method' => 'PUT',  'path' => '/customers/{code}',  'id_path' => 'data.id'],
    'find_invoice' => [
        'method'      => 'GET',
        'path'        => '/invoices/{number}',
        'id_path'     => 'data.id',
        'number_path' => 'data.number',
        'status_path' => 'data.status',
        'query'       => ['include' => 'items'],
    ],
    'health'       => ['method' => 'GET', 'path' => '/health', 'id_path' => null],
];
```

جای‌نگهدارها: `{number}`، `{external_id}`، `{code}`. مقادیر `query` را رمزگذاری‌نشده بنویسید؛
کتابخانه یک‌بار کد می‌کند.

### ۳.۳. نگاشت

از `dryRun: true` برای دیدن بدنه‌ی دقیق استفاده کنید. اگر ساختار مقصد پوشش (envelope) دارد، همان را
در مسیرهای مقصد بنویسید. جزئیات: [`mapping-fa.md`](mapping-fa.md).

### ۳.۴. مخزن idempotency

```php
$store = new \IranAccounting\Idempotency\PdoIdempotencyStore($pdo, table: 'iran_accounting_idempotency');
$store->migrate();   // یک‌بار در دیپلوی؛ همه‌ی دستورها IF NOT EXISTS دارند
```

`ArrayIdempotencyStore` فقط برای تست و ورکر کوتاه‌عمر است. برای چند سرور، مخزن مشترک (MySQL) لازم است.

## ۴. آزمون پذیرش قبل از تولید

هر مورد را روی **شرکت آزمایشی** انجام دهید و نتیجه را ثبت کنید:

1. **dry-run**: بدنه‌ی تولیدشده را با نمونه‌ی مستندات مقایسه کنید. هیچ تماس شبکه‌ای نباید رخ دهد.
2. **یک سند واقعی**: فاکتور ساده با یک ردیف، مالیات ۹٪، مشتری موجود. سپس سند را در خود نرم‌افزار
   حسابداری باز کنید و مبلغ، تاریخ و کد مشتری را کنترل کنید.
3. **تکرار**: همان `external_id` را دوباره بفرستید. باید `duplicate` شود و تعداد فراخوانی مقصد
   افزایش نیابد.
4. **تغییر محتوا**: همان `external_id` با مبلغ متفاوت. باید `duplicate` + هشدار `IR-IDEM-002` شود.
5. **خطای اعتبارسنجی**: کد ملی نامعتبر. باید `IR-VAL-005` با مقدار ماسک‌شده برگردد و هیچ ارسالی نباشد.
6. **خطای موقت**: با قطع شبکه یا پاسخ 503، رفتار تلاش مجدد را ببینید. اگر آداپتر کلید idempotency
   نمی‌فرستد، باید فقط یک تلاش انجام شود و `IR-IDEM-003` برگردد.
7. **سلامت**: `healthCheck()` را در پایش قرار دهید؛ «unknown» یعنی اندپوینت health تنظیم نشده است.
8. **مغایرت‌یابی**: یک سند را در مقصد حذف/ابطال کنید و بررسی کنید رویه‌ی بازیابی شما آن را تشخیص دهد.

## ۵. اجرا در تولید

* ورکر را از صف تغذیه کنید؛ نتیجه‌ی `SyncResult` را در صف ذخیره کنید.
* `SyncStatus::Invalid` را قرنطینه کنید؛ تلاش دوباره بدون اصلاح سند بی‌فایده است.
* `SyncStatus::Failed` را با backoff دوباره در صف بگذارید؛ `errors[0]->code` را نگه دارید.
* `SyncStatus::Duplicate` را موفق تلقی کنید، مگر اینکه هشدار `IR-IDEM-002` داشته باشد.
* لاگ را با `SyncResult::toLogArray()` بسازید؛ این شکل `payload` (حاوی PII) را حذف می‌کند.
* `attempts` و `delaysMs` را در لاگ نگه دارید تا رفتار retry قابل بازبینی باشد.
* حداکثر هم‌زمانی را در صف محدود کنید؛ این بسته rate limiter ندارد.

نمونه‌ی لاگ:

```php
$logger->info('accounting.push', $result->toLogArray());
```

## ۶. مغایرت‌یابی

سه حالت نیاز به اقدام انسانی دارد:

| حالت | نشانه | اقدام |
| --- | --- | --- |
| مقصد موفق، ثبت محلی ناموفق | `failed` + هشدار «مغایرت‌یابی دستی» + `remote_id` | سند را در مقصد جست‌وجو کنید؛ اگر هست، رکورد محلی را کامل کنید؛ دوباره ارسال نکنید |
| کلید در اختیار ورکر مرده | `duplicate` + `IR-IDEM-001` تا پایان TTL | TTL قفل را متناسب با کندترین پوش تنظیم کنید؛ پس از TTL reclaim می‌شود |
| سند در مقصد حذف شده | `duplicate` با `remote_id` قدیمی | سند جدید با `external_id` جدید بسازید یا در مقصد اصلاح کنید |

## ۷. چک‌لیست امنیتی

- [ ] توکن فقط از محیط/فایل امن خوانده می‌شود و در مخزن نیست.
- [ ] `base_uri` تحت کنترل اپراتور است و egress سرور به همان مقصد محدود شده است.
- [ ] TLS روشن است؛ برای گواهی داخلی از `CurlClient(caBundle: ...)` استفاده شده، نه خاموش کردن verify.
- [ ] پیکربندی و لاگ‌ها دسترسی فایل محدود دارند.
- [ ] لاگ‌ها payload کامل را ثبت نمی‌کنند (`toLogArray()`).
- [ ] خطاهای مقصد با `safeBody()` یا پیام‌های کتابخانه ثبت می‌شوند، نه `responseBody` خام.
- [ ] ورکر با کاربر سیستمی کم‌دسترسی اجرا می‌شود و دسترسی نوشتن به جدول idempotency دارد.
- [ ] نسخه‌ی PHP حداقل 8.1 است (ماتریس CI: 8.1–8.4) و `composer audit` در CI اجرا می‌شود.

## ۸. پرسش‌های کشف اندپوینت

از مستندات یا تیم فنی مشتری بپرسید:

1. احراز هویت چگونه است (Bearer، API key، Basic، امضای درخواست)؟
2. ایجاد فاکتور idempotent است؟ آیا هدر یا فیلد کلید تکرار وجود دارد؟
3. پاسخ موفق چه شکلی دارد و شناسه‌ی سند کجاست؟
4. خطای «سند تکراری» چه کد HTTP/بدنه‌ای دارد؟ (`duplicate_codes`)
5. تاریخ شمسی است یا میلادی؟ قالب دقیق؟
6. مالیات در سطح سند است یا ردیف؟ درصد یا مبلغ؟
7. مشتری باید از قبل وجود داشته باشد؟ با کد یا شناسه؟
8. محدودیت نرخ، اندازه‌ی بدنه یا پنجره‌ی زمانی (سال مالی بسته) وجود دارد؟
9. نسخه‌ی محصول و افزونه‌ها چیست؟ آیا با نسخه‌ی دیگری تفاوت دارد؟
10. محیط آزمایشی جدا وجود دارد یا باید در شرکت آزمایشی همان نصب کار کرد؟

## ۹. عیب‌یابی سریع

| نشانه | احتمال | بررسی |
| --- | --- | --- |
| `IR-CFG-001` | `base_uri` خالی/نامعتبر یا مسیر مطلق cross-origin | مقدار و origin را ببینید |
| `IR-CFG-002` | اندپوینت `invoice` نیست یا `__FILL_` باقی مانده | پروفایل را کامل کنید |
| `IR-MAP-001` | فیلد الزامی در سند نیست | `dryRun` و `context.source_path` |
| `IR-ADP-001` | پاسخ HTML به‌جای JSON | وضعیت HTTP و لاگ امن سرور مقصد |
| `IR-ADP-002` | `id_path` با پاسخ واقعی نمی‌خواند | نمونه‌ی پاسخ موفق را بگیرید |
| `IR-VAL-003` | اختلاف بیش از ۱ ریال در جمع | قاعده‌ی گردکردن مبدأ را با حسابدار نهایی کنید |
| `IR-IDEM-003` | آداپتر کلید idempotency نمی‌فرستد | هدر را تنظیم کنید یا شکست را دستی بررسی کنید |
| `IR-DB-001` | مخزن در دسترس نیست | اتصال/جدول/مجوز دیتابیس؛ کتابخانه fail-closed است |

* مسیر لاگ و هشدارهای `IR-IDEM-002` / `IR-IDEM-003` / `IR-DB-001`.
